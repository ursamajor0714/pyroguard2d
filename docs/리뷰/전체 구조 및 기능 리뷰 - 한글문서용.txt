• next 16.2.11 (Vercel사 개발, 오픈소스)

[무엇] React 기반 풀스택 웹 프레임워크.
프론트엔드(React UI)와 백엔드(API Route Handlers)를 한 프로젝트 안에서 통합 구현 가능.

[왜 채택]
1) 프론트+백엔드 통합: 별도의 Express/Nest 서버 없이 app/api/ 폴더에 route.ts만 만들면
센서 CRUD, OTP 인증, 층별 현황 같은 백엔드 API가 자동으로 생성됨.
→ 소방 관제 시스템 특성상 프론트(2D 도면 UI)와 백엔드(센서 DB, AI 분석)가
밀접하게 연동되어야 하므로, 이를 한 프로젝트에서 관리하는 것이 개발·배포 효율 극대화.
2) 파일 기반 라우팅: app/page.tsx → '/' 메인, app/mobile-demo/page.tsx → '/mobile-demo'
별도 라우터 설정 없이 폴더 구조만으로 URL 경로가 자동 매핑됨.
3) Server Component / Client Component 이원 구조:
- 폰트 로딩, SEO 메타데이터 같은 정적 부분은 Server Component(layout.tsx)에서 처리 → 번들 크기 절감
- 줌/팬, 드래그, 경보 사운드 같은 인터랙티브 부분만 Client Component('use client')로 격리
4) Middleware(middleware.ts): 모든 API 요청에 HTTPS, CORS, CSP 보안 정책을 자동 적용.
별도의 nginx/apache 설정 없이도 보안 계층 구현 가능.
5) 최신 React 19 공식 지원 및 Turbopack 번들러로 개발 서버 핫 리로드 속도 극대화.

[어디서 사용] 프로젝트 전체의 기반 프레임워크. 모든 파일이 Next.js 위에서 동작.

• react 19.2.4 (Meta/Facebook사 개발, 오픈소스)

[무엇] UI 컴포넌트 렌더링 라이브러리. JSX 문법으로 화면을 선언적으로 구성.

[왜 채택]
1) 컴포넌트 기반 설계: 소방 관제 시스템은 센서 노드, CCTV 모달, 층 선택기, 도면 캔버스 등
수십 개의 독립적인 UI 블록으로 구성됨 → React의 컴포넌트 단위 분리가 딱 맞는 구조.
2) 가상 DOM: 센서 60여 개 노드의 상태(NORMAL/ALARM/OFFLINE)가 3초마다 변경되는데,
React의 가상 DOM 비교(Diffing)가 변경된 노드만 골라서 최소 업데이트 → 대량 센서 실시간 갱신 성능 확보.
3) 훅(Hooks) 시스템: useState, useEffect, useRef, 커스텀 훅(useD3Zoom, useSensorDrag 등)으로
줌/팬 상태, 드래그 좌표, 타이머 같은 복잡한 로직을 깔끔하게 분리 가능.
4) 생태계: Zustand(상태 관리), Framer Motion(애니메이션), Lucide(아이콘) 등
React 전용 패키지 생태계가 가장 풍부하여 의존성 선택지가 넓음.
5) Next.js 16.2의 공식 런타임이 React 19를 요구함.

[어디서 사용] 모든 .tsx 컴포넌트 파일 (page.tsx, FloorCanvas.tsx, 모달 6종, 사이드바 등 전부)

• react-dom 19.2.4 (Meta/Facebook사 개발, react와 세트)

[무엇] React가 만든 가상 DOM을 실제 브라우저 HTML DOM에 그려주는 렌더링 바인딩 라이브러리.

[왜 필요한가 — react와 분리된 이유]
React 코어(react 패키지)는 "UI를 어떻게 구성할지" 선언하는 엔진이고,
react-dom은 "그 선언을 어디에 그릴지" 결정하는 출력 타겟임.

React 코어가 렌더링 타겟을 분리한 이유:
- 웹 브라우저에 그리려면 → react-dom (HTML DOM)
- 모바일 앱에 그리려면 → react-native (iOS/Android 네이티브 뷰)
- 3D VR에 그리려면 → react-three-fiber (WebGL/Three.js)
- 터미널에 그리려면 → ink (CLI 텍스트 UI)

즉, react-dom은 "이 프로젝트는 웹 브라우저에서 돌아가는 앱입니다"를 선언하는 패키지.
react만 설치하면 어디에 그릴지 모르기 때문에 화면이 나오지 않음.
이 프로젝트는 웹 관제 시스템이므로 react-dom이 반드시 필요.

[어디서 사용] Next.js 내부에서 자동으로 사용됨 (직접 import하는 코드는 없지만,
Next.js가 빌드/렌더링 시 react-dom을 호출하여 모든 컴포넌트를 브라우저 DOM에 마운트)

• typescript ^5 (Microsoft사 개발, 오픈소스)

[무엇] JavaScript에 정적 타입 시스템을 추가한 상위 언어. .ts/.tsx 파일로 작성하며
빌드 시 순수 JavaScript로 컴파일됨.

[왜 JS가 아닌 TS를 선택했는가]
1) 소방 관제 시스템의 안정성 요구:
센서 상태가 'NORMAL' | 'ALARM' | 'MAINTENANCE' | 'OFFLINE' 4가지뿐인데,
JS에서는 오타로 'ALRAM'이라고 써도 에러 없이 실행됨 → 현장에서 경보가 씹히는 치명적 버그 발생 가능.
TS는 SensorStatus 타입으로 허용값을 제한하여 컴파일 단계에서 오타/오입력 100% 차단.

2) 센서 노드 데이터 구조 강제:
SensorNode 인터페이스로 { id, type, floorId, x, y, status, fov?, doorState? } 등
40여 개 필드의 구조를 명확히 정의 → API 요청/응답, 스토어 저장, 컴포넌트 렌더링 전 구간에서
데이터 형태 불일치 오류를 사전 방지.

3) IDE 자동완성/리팩토링 지원:
SensorType을 'EXTINGUISHER'에서 'FIRE_EXTINGUISHER'로 바꾸면 TS가 관련된 모든 파일의
사용처를 즉시 빨간 줄로 표시 → 누락 수정 제로.
JS에서는 문자열 검색에 의존해야 하고, 동적 타입이라 런타임에서야 버그 발견.

4) Next.js 16.2 공식 권장:
create-next-app 기본 템플릿이 TypeScript이며, Next.js의 Metadata, NextRequest,
NextResponse 등 프레임워크 타입이 TS 환경에서 최적화되어 있음.

5) 코드 문서화 효과:
types/sensor.ts, types/floor.ts, types/fireLog.ts 같은 타입 정의 파일이
그 자체로 데이터 사전(Data Dictionary) 역할을 하여 별도 API 문서 없이도
센서/층/점검이력의 데이터 구조를 한눈에 파악 가능.

[설정] tsconfig.json: target ES2017, jsx react-jsx, strict true, paths @/* → ./*
[어디서 사용] 프로젝트의 모든 .ts, .tsx 파일 (100%)

1.2 UI 애니메이션 & 아이콘

• framer-motion ^12.42.2 (Framer사 개발, 오픈소스)

[무엇] React 전용 선언적 애니메이션 라이브러리.
<motion.div animate={{...}}> 한 줄로 복잡한 트랜지션/모션 구현.

[왜 채택 — CSS 애니메이션이나 다른 라이브러리가 아닌 이유]
1) 마운트/언마운트 애니메이션: 모달이 열릴 때 페이드인, 닫힐 때 페이드아웃을
AnimatePresence 컴포넌트로 간단히 처리. CSS만으로는 DOM에서 제거되는 순간의
퇴장 애니메이션 구현이 매우 복잡하지만, framer-motion은 exit prop 하나로 해결.
2) 레이아웃 애니메이션: 건물 조감도(BUILDING) ↔ 2D 도면(CANVAS) 뷰 전환 시
layout prop으로 요소 위치/크기 변화를 자동 보간 → 부드러운 전환 효과.
3) React 상태와 직접 연동: animate={{ scale: isAlarm ? 1.2 : 1 }} 처럼
React state 변경이 곧바로 애니메이션에 반영 → 별도 명령형 코드 불필요.
4) 성능: 내부적으로 requestAnimationFrame + GPU 가속(transform/opacity)을 자동 적용.
GSAP 같은 라이브러리는 React와 별개 라이프사이클이라 동기화 이슈 발생 가능.
5) 번들 사이즈 트리쉐이킹: motion.div, AnimatePresence만 import하면
사용하지 않는 기능은 빌드에서 자동 제거.

[사용 API] motion.div, AnimatePresence, animate, initial, exit, layout, transition
[어디서 사용] 뷰 전환(page.tsx), 모달 6종, AlarmCenterToast, FloorSelector 탭 전환

• lucide-react ^1.26.0 (Lucide 커뮤니티, 오픈소스 — Feather Icons 포크)

[무엇] SVG 아이콘 라이브러리. React 컴포넌트로 1,500종 이상의 아이콘 제공.

[왜 채택 — FontAwesome/Material Icons가 아닌 이유]
1) 트리쉐이킹: import { Flame } from 'lucide-react' 처럼 개별 아이콘만 import하면
나머지 1,400개 아이콘은 빌드에서 완전 제거 → 번들 사이즈 최소화.
FontAwesome은 전체 폰트 파일을 로드해야 해서 무거움.
2) SVG 네이티브: 각 아이콘이 순수 SVG React 컴포넌트 → className, size, color prop으로
Tailwind CSS와 즉시 호환. 폰트 방식과 달리 크기 조절 시 흐림/깨짐 없음.
3) 일관된 디자인: 모든 아이콘이 24px 기준, 2px stroke, 라운드 캡으로 통일
→ 소방 관제 대시보드의 센서 아이콘(🔥 Flame, ⚡ Zap, 💧 Droplet 등)이
시각적으로 균일하고 깔끔하게 표출.
4) 라이선스: ISC 라이선스 (상업용 무료 사용 가능).

[어디서 사용] Icons.tsx (센서 아이콘 매퍼), FloorSelector (메뉴 아이콘 20종+),
모달 6종 (액션 버튼 아이콘), page.tsx (헤더 아이콘), SensorPalette (팔레트 아이콘)
→ 프로젝트 전역에서 50종 이상의 아이콘 사용 중

1.3 2D 캔버스 줌/팬 조작

• d3-selection ^3.0.0 + d3-zoom ^3.0.0 (D3.js, Mike Bostock 개발, 오픈소스)

[무엇]
d3-selection: DOM 요소를 선택(select)하고 이벤트를 바인딩하는 유틸리티.
d3-zoom: 마우스 휠 줌, 터치 핀치 줌, 드래그 팬을 처리하는 전문 라이브러리.
(※ D3.js 전체를 설치하지 않고, 필요한 서브 모듈 2개만 개별 설치하여 번들 경량화)

[왜 이 기능이 필요한가 — 2D 소방 관제에서 줌/팬이 왜 필수인가]
1) 실제 사무빌딩 한 개 층이 300~400평(약 1000㎡) 규모이므로,
1:1 축척 도면은 화면에 다 들어오지 않음 → 확대해서 특정 구역을 자세히 봐야 함.
2) 센서 60여 개가 한 도면에 배치되어 있어, 축소해서 전체 레이아웃을 조망하거나
확대해서 개별 센서 상태를 확인하는 줌인/줌아웃이 현장 관제의 핵심 동작.
3) 긴급 화재 시 특정 구역(예: B2 전기차 충전소)만 빠르게 확대하여 CCTV 위치/화각 확인.

[왜 d3-zoom인가 — 직접 구현이 아닌 이유]
1) 줌/팬을 직접 구현하면 고려해야 할 예외가 극히 많음:
- 줌 배율 경계값 바운스백 (0.5x 이하, 5.0x 이상에서 튕겨내기)
- 줌 중심점 계산 (마우스 커서 위치 기준 확대, 화면 중앙 고정이 아님)
- 터치 핀치 제스처 + 마우스 휠 동시 지원
- 줌과 팬의 관성(inertia) 처리
→ d3-zoom은 이 모든 것을 수학적으로 완성된 상태로 제공하는 사실상 업계 표준 라이브러리.
2) SVG transform 동기화: d3-zoom은 SVG의 transform="translate(x,y) scale(s)"를
직접 조작하므로 CSS transform보다 SVG 캔버스와의 호환성이 완벽.
3) 이벤트 필터링: .filter()로 마우스 휠/멀티터치만 줌에 반응하고,
싱글 터치 드래그는 센서 노드 이동에 양보하는 세밀한 제어 가능.
4) 더블클릭 줌 비활성화: .on('dblclick.zoom', null)로 CCTV 노드 더블클릭(라이브 모달 열기)과
충돌하지 않도록 처리.
5) D3 전체(30개+ 서브 모듈, 수백 KB)를 설치하지 않고 d3-selection + d3-zoom
2개만 cherry-pick하여 최소 번들 유지.

[사용 API] select(), zoom(), zoomIdentity, scaleExtent([0.5, 5.0]), .filter(), .on()
[어디서 사용] hooks/useD3Zoom.ts → FloorCanvas.tsx에서 SVG 캔버스에 적용

1.4 CSS 유틸리티

• tailwindcss ^4 (Tailwind Labs사 개발, 오픈소스)

[무엇] 유틸리티 퍼스트(Utility-First) CSS 프레임워크.
className="bg-slate-900 text-white p-4 rounded-lg" 처럼
HTML/JSX 안에서 직접 스타일을 조합하는 방식.

[왜 채택 — 순수 CSS나 CSS-in-JS가 아닌 이유]
1) 다크 테마 관제 UI: 소방 관제실은 24시간 상시 모니터링하므로 눈 피로를 줄이는
다크 테마가 필수 → bg-slate-900, bg-[#060913] 같은 다크 컬러를 인라인으로
빠르게 적용할 수 있어 개발 속도가 빠름.
2) 상태별 동적 스타일: 센서 ALARM 시 border-red-500, NORMAL 시 border-emerald-500 같은
조건부 스타일 전환이 className 조합으로 간결하게 처리됨.
3) 반응형: md:w-[270px], lg:grid-cols-4 같은 브레이크포인트 유틸리티로
관제 데스크톱(1920px)과 모바일 시연기(375px) 동시 대응.
4) 프로덕션 자동 퍼지: 실제 사용된 클래스만 빌드에 포함 → CSS 파일 크기 최소화.
5) v4 최신 문법: @import "tailwindcss" + @theme inline으로 설정 파일 없이
CSS 파일 안에서 직접 테마 토큰 정의 가능.

[어디서 사용] 모든 컴포넌트의 className (프로젝트 전역)

• @tailwindcss/postcss ^4 (Tailwind Labs사)

[무엇] Tailwind CSS를 PostCSS 빌드 파이프라인에 연결하는 플러그인.
[왜 필요] Next.js는 CSS 처리에 PostCSS를 사용하는데, Tailwind v4가 PostCSS 플러그인으로
동작하기 위해 이 패키지가 반드시 필요함. 없으면 Tailwind 클래스가 CSS로 변환되지 않음.
[어디서 사용] postcss.config.mjs에서 플러그인으로 등록

• clsx ^2.1.1 (Luke Edwards 개발, 오픈소스)

[무엇] 조건부 className 합성 유틸리티. 용량 228 bytes (초경량).
[왜 채택]
센서 상태에 따라 className이 동적으로 바뀌어야 하는데:
❌ 삼항 연산자 중첩: className={`${status === 'ALARM' ? 'border-red-500' : ''} ${status === 'NORMAL' ? 'border-emerald-500' : ''}`}
✅ clsx 사용: className={clsx('border', { 'border-red-500': status === 'ALARM', 'border-emerald-500': status === 'NORMAL' })}
→ 가독성, 유지보수성 대폭 향상.
[어디서 사용] SensorNode, FovOverlay, Badge, Button, FloorSelector 등 상태별 스타일 전환 컴포넌트

• tailwind-merge ^3.6.0 (dcastil 개발, 오픈소스)

[무엇] Tailwind CSS 클래스 충돌 해결 유틸리티.
[왜 채택]
예: "p-4 p-2" → Tailwind은 둘 다 적용하여 예측 불가 결과 발생.
tailwind-merge는 후순위 "p-2"만 남기고 "p-4"를 자동 제거하여 충돌 해결.
컴포넌트에 기본 스타일 + 외부 className props가 합쳐질 때 필수.
[어디서 사용] Button, Badge 등 공통 UI 컴포넌트에서 외부 className 주입 시 충돌 방지

1.5 미디어 스트리밍

• hls.js ^1.6.16 (video-dev 커뮤니티, 오픈소스)

[무엇] HLS(HTTP Live Streaming) 프로토콜을 브라우저에서 재생하는 라이브러리.

[왜 채택 — CCTV 라이브 스트리밍에 HLS가 필요한 이유]
1) 대부분의 IP CCTV는 RTSP 프로토콜로 영상을 전송하는데,
웹 브라우저는 RTSP를 직접 재생할 수 없음 (보안상 차단).
2) RTSP → HLS 변환 서버(FFmpeg/Nginx-RTMP 등)를 거쳐 .m3u8 스트림으로 변환하면,
hls.js가 이 스트림을 브라우저의 <video> 태그에 실시간 연결하여 재생.
3) MJPEG(IP 카메라의 HTTP 스트림) 방식 폴백: hls.js 없이도 <img src={url} />로
MJPEG 직접 표출 가능하도록 이중 대응.
4) 적응형 비트레이트(ABR): 네트워크 상태에 따라 자동으로 화질 조절
→ 관제실 네트워크 부하 시에도 영상 끊김 최소화.

[어디서 사용] CctvLiveModal.tsx (단일 CCTV 라이브),
CctvMultiMatrixModal.tsx (다채널 비디오월 2x2/3x3/4x4)

1.8 전역 상태 관리

• zustand (pmndrs 커뮤니티, 오픈소스 — MIT 라이선스)

[무엇] React 전역 상태 관리 라이브러리. Redux 대비 보일러플레이트 90% 감소.
create() 한 줄로 스토어 생성, 훅(useStore)으로 바로 사용.

[왜 채택 — Redux/Recoil/Jotai가 아닌 이유]
1) 보일러플레이트 제로: Redux는 Action Type, Action Creator, Reducer, Store, Provider,
connect/useSelector 등 파일 7~8개가 필요. Zustand는 하나의 .ts 파일에
상태 + 액션을 모두 정의하고 끝 → 소방 관제 시스템처럼 빠르게 기능 추가해야 할 때 유리.
2) React 외부에서도 접근 가능: useCanvasStore.getState().setViewMode('BUILDING') 처럼
컴포넌트 밖(이벤트 핸들러, 타이머 콜백)에서도 스토어에 직접 접근 가능.
Redux는 반드시 React 컴포넌트 안에서 dispatch해야 함.
3) 5개 스토어 독립 운영: useCanvasStore, useSensorStore, useOccupantStore,
useEvChargerStore, useFireLogStore가 각각 독립 → 한 스토어 변경이
다른 스토어의 리렌더링을 유발하지 않음 (성능 격리).
4) 번들 크기: zustand는 ~1KB (gzip). Redux Toolkit은 ~12KB.
5) TypeScript 친화: 제네릭 타입 추론이 자동으로 작동하여 별도 타입 정의 최소화.

[주의] package.json에는 zustand가 명시되어 있지 않지만, 프로젝트 내 5개 스토어 파일이
모두 import { create } from 'zustand'를 사용하고 있으므로 실제 설치되어 있음.
(node_modules 내 존재 확인 필요 — 또는 다른 패키지의 의존성으로 설치되었을 가능성)

[어디서 사용]
store/useCanvasStore.ts — 캔버스 UI 제어 (뷰 모드, 줌, 팬, 잠금, 모달 플래그)
store/useSensorStore.ts — 센서 노드 CRUD + API 동기화
store/useOccupantStore.ts — 잔류 인원 구조 추적
store/useEvChargerStore.ts — B2 EV 충전기 관리
store/useFireLogStore.ts — 소방점검 이력 관리

📡 7. API 엔드포인트 & 데이터 흐름 정리

[API 1] GET /api/sensors?floorId=xxx
요청: 층 ID (선택, 없으면 전체)
처리: getSensorsFromDb(floorId) → DynamoDB Scan 또는 localMemoryDb 필터
응답: { success: true, data: SensorNode[] }
소비자: app/page.tsx (3초 폴링), mobile-demo/page.tsx (5초 폴링)

[API 2] POST /api/sensors
요청: SensorNode 객체 (id, type, floorId 필수)
처리: 유효성 검증 → saveSensorToDb(sensor) → DynamoDB Put 또는 localMemoryDb push
응답: { success: true, message: '센서 등록 완료' }
소비자: useSensorStore.addNode(), mobile-demo/page.tsx

[API 3] PUT /api/sensors
요청: { id: string, ...갱신 필드 }
처리: updateSensorInDb(id, fields) → DynamoDB Update 또는 localMemoryDb assign
특수: sensor-ev-smoke + ALARM → { triggerAutoFloorChange: 'B2' }
응답: { success: true, message: '센서 업데이트 완료' }
소비자: useSensorStore (updateNode/triggerAlarm/resolveAlarm/updateDoorState),
mobile-demo/page.tsx

[API 4] DELETE /api/sensors?id=xxx
요청: 센서 ID (쿼리 파라미터)
처리: deleteSensorFromDb(id) → DynamoDB Delete 또는 localMemoryDb filter
응답: { success: true, message: '센서 삭제 완료' }
소비자: useSensorStore.deleteNode()

[API 5] GET /api/floors
요청: 없음
처리: getSensorsFromDb() → FLOOR_LIST 순회 → 층별 센서 수/경보/상태 집계
상태 우선순위: ALARM > OFFLINE > MAINTENANCE > NORMAL
응답: { success: true, data: FloorStatusInfo[] }

[API 6] GET /api/emergency
요청: streamUrl (선택, 비디오 소스 경로)
처리:
미승인 → { approved: false, peopleCount: 0 }
승인됨 → exec('python ai_detector.py') → 스냅샷 생성 → 결과 반환
Python 실패 → 01.mockup.jpg 폴백 복사
응답: { success, approved, peopleCount, snapshotBestUrl, snapshotFallbackUrl }
소비자: app/page.tsx (10초 폴링, OTP 승인 시에만)

[API 7] POST /api/emergency
요청 A: { otp: '119119' } → 세션 승인
요청 B: { action: 'REVOKE' } → 세션 해제
처리: 인메모리 isOtpApprovedPersistent 플래그 토글
응답: { success: true, approved: boolean, message: string }
소비자: EmergencyOtpModal.tsx (인증), useEmergencyTimer.ts (해제)
