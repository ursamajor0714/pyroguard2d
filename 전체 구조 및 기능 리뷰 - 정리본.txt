  [1] 프로젝트 핵심 아키텍처 한눈에 보기
================================================================================

  ■ 시스템명: PyroGuard 2D (2D CAD 기반 소방 방재 관제 시스템)
  ■ 핵심 목적: 
    - 오피스 빌딩 20개 층의 소방 센서·CCTV·비상문 상태를 2D CAD 도면 위에서 실시간 관제.
    - 119 긴급 상황 발생 시 OTP 승인 후 인원 위치 정보 해독 및 층별/빌딩 전체 구조 조망.
  ■ 아키텍처 특징:
    - Next.js 16.2 App Router 기반 **프론트+백엔드 단일 통합 프로젝트**.
    - 외부 클라우드/AI 의존성 없는 **순수 로컬 초고속 인메모리 방재 데이터베이스** 탑재.
    - SVG getScreenCTM() 역행렬 좌표 변환을 통한 줌/팬 연동 센서 노드 드래그 앤 드롭.
    - Tailscale / WebRTC / DroidCam 호환 iframe 기반 CCTV 실시간 라이브 스트리밍.
  ■ 시스템 규모: 20개 층(B3~ROOF, 외부), 센서 노드 164개, 모달 6종, API 7개, 스토어 5개.

  【카테고리 1: 프레임워크 & 아키텍처 설계 (Architecture)】

  Q1. Next.js App Router를 채택한 핵심 아키텍처적 이유는 무엇인가요?
  → 프론트엔드와 백엔드 API Route Handlers를 한 프로젝트에서 관리하여 소방 데이터 
    연동 효율을 높이고, 정적 요소(Server Component)와 동적 인터랙션(Client Component)을 
    분리하여 클라이언트 자바스크립트 번들 용량을 절감하기 위함입니다.

  Q2. Server Component와 Client Component를 어떻게 구분하여 구현했나요?
  → layout.tsx(웹폰트, SEO 메타데이터, 전역 CSS)는 Server Component로 처리하고, 
    줌/팬, 센서 드래그, Web Audio, 모달 등 사용자와 상호작용하는 모든 뷰 컴포넌트는 
    Client Component('use client')로 격리했습니다.

  Q3. 백엔드 전용 서버(Express/NestJS)를 따로 두지 않고 Next.js API Routes를 쓴 장점은?
  → 별도의 서버 세팅, 포트 분리, CORS 복잡성 없이 `/app/api/` 폴더 내 `route.ts` 파일만으로 
    RESTful API를 즉시 구축할 수 있어 개발 생산성과 배포 유지보수성이 극대화됩니다.

  Q4. 외부 DB(MySQL/MongoDB) 대신 로컬 인메모리 스토어 모듈을 구축한 이유는?
  → 관제 시스템 시연 시 클라우드 네트워크 지연이나 외부 DB 의존 없이 
    무중단 초고속 응답(0ms)을 보장하고, 서버 실행 즉시 20개 층 방재 시드 데이터를 
    완벽하게 제공하기 위함입니다.

  Q5. 싱글 페이지 애플리케이션(SPA) 뷰 전환 구조는 어떻게 설계되었나요?
  → 라우팅 이동 없이 `useCanvasStore`의 `viewMode`('BUILDING' ↔ 'CANVAS') 상태값 전환과 
    Framer Motion 애니메이션을 조합하여 화면 튕김 없는 부드러운 뷰 전환을 구현했습니다.


  【카테고리 2: 2D CAD & SVG 조작 수학/알고리즘 (2D CAD & Math)】

  Q6. SVG 도면 조작 시 왜 D3-Zoom 라이브러리를 채택했나요?
  → 줌 중심점(마우스 커서 위치) 계산, 0.5x~5.0x 배율 제한, 터치 핀치 제스처, 관성 처리 
    등의 복잡한 2D 수학 알고리즘이 검증된 업계 표준 라이브러리이기 때문입니다.

  Q7. SVG 캔버스가 줌/팬으로 변형된 상태에서 센서 드래그 좌표는 어떻게 계산하나요?
  → SVG containerG 요소의 `getScreenCTM().inverse()` 역행렬 변환 API를 사용하여 
    화면 마우스 좌표를 SVG 내부 절대 좌표(0~1200, 0~800)로 정확히 역변환합니다.

  Q8. CCTV FOV(화각) 부채꼴 패스는 어떻게 생성되나요?
  → `canvasMath.ts`에서 삼각함수(`Math.cos`, `Math.sin`)를 이용하여 카메라 위치, 거리, 
    화각, 회전각을 기반으로 SVG `<path d="M ... A ... Z">` 부채꼴 Arc 호를 생성합니다.

  Q9. FOV 조작 핸들 작동 시 Snap(스냅) 기능은 어떻게 처리했나요?
  → distance(1m 단위), angle(15° 단위), rotation(45° 단위) 값을 `Math.round(val / step) * step` 
    유틸리티 함수로 처리하여 직관적인 궤적 스냅을 조작할 수 있게 구현했습니다.

  Q10. 도면 캔버스 확대 시 노드 및 텍스트의 크기 비틀림을 어떻게 방지했나요?
  → SVG `viewBox="0 0 1200 800"` 고정 비율과 `preserveAspectRatio="xMidYMid meet"` 
    설정을 통해 캔버스 비율을 일정하게 유지하고 개별 노드를 그룹(`<g>`) 단위로 관리했습니다.


  【카테고리 3: 전역 상태 관리 & 성능 최적화 (State & Performance)】

  Q11. 왜 Redux가 아닌 Zustand를 선택했나요?
  → Redux 대비 파일 수와 보일러플레이트 코드가 90% 이상 적고, 1KB 미만의 초경량 
    라이브러리이며, React 컴포넌트 밖(이벤트 핸들러, 타이머)에서도 direct 접근이 가능하기 때문입니다.

  Q12. Zustand 스토어를 1개가 아닌 5개로 분리한 이유는 무엇인가요?
  → useCanvasStore, useSensorStore, useOccupantStore, useEvChargerStore, useFireLogStore로 
    도메인을 분리하여 한 스토어의 변경이 다른 스토어 컴포넌트의 불필요한 리렌더링을 유발하지 않도록 성능을 격리했습니다.

  Q13. 60여 개 센서 노드가 3초마다 폴링될 때 성능 저하가 없는 이유는?
  → React 가상 DOM의 비교(Diffing) 알고리즘이 변경된 속성 노드만 최소 업데이트하고, 
    Zustand 구독 훅이 필요한 데이터 필드만 선택적으로 렌더링하기 때문입니다.

  Q14. 층 변경 시(setFloor) 줌/팬 상태는 어떻게 관리되나요?
  → 층이 바뀔 때마다 `useCanvasStore.setFloor()` 내부에서 D3 transform 객체를 
    `zoomIdentity`(scale 1.0, pan 0,0)로 자동 리셋시켜 새 도면이 정중앙에 배치되게 처리했습니다.

  Q15. 모달 오픈 시 배경 캔버스 인터랙션 차단은 어떻게 처리했나요?
  → 모달 오버레이 배경에 `e.stopPropagation()` 및 `backdrop-blur` 클래스를 적용하고, 
    `useCanvasStore`의 `isLocked` 상태를 통해 드래그 앤 드롭을 차단했습니다.


  【카테고리 4: 백엔드 API & 데이터 구조 (Backend & Data)】

  Q16. GET /api/floors 엔드포인트의 층 종합 상태 도출 로직은?
  → 20개 층을 순회하며 해당 층 노드들의 status를 검사하여 `ALARM > OFFLINE > MAINTENANCE > NORMAL` 
    우선순위 규칙에 따라 가장 높은 위험도 상태를 층의 대표 상태로 결정합니다.

  Q17. PUT /api/sensors 호출 시 B2 전기차 화재 트리거 작동 방식은?
  → `id === 'sensor-ev-smoke'` 노드가 `ALARM` 상태로 변경되면 API 응답에 
    `triggerAutoFloorChange: 'B2'` 응답 값을 실어 보내 프론트엔드가 자동으로 B2 도면으로 이동하도록 합니다.

  Q18. DELETE /api/sensors 호출 시 캔버스 연동은?
  → 도면 바깥으로 센서를 드래그 앤 드롭하면 `useSensorDrag`가 캔버스 영역(0~100%) 이탈을 감지하여 
    API DELETE를 호출하고 스토어 노드 배열에서 해당 센서를 즉시 제거합니다.

  Q19. SensorNode 데이터 인터페이스 설계 시 옵셔널 필드(? )를 활용한 이유는?
  → 모든 센서에 필요하지 않은 속성(CCTV 전용 `fov`, 비상문 전용 `doorState`/`powerStatus`, 
    수압계 전용 `value`)을 선택적 필드로 설계하여 메모리 낭비를 줄이고 데이터 유연성을 확보했습니다.

  Q20. 백엔드 API 에러 발생 시 처리 메커니즘은?
  → 모든 API Route Handler를 `try-catch` 블록으로 감싸고, 실패 시 HTTP 500/400/401 
    상태 코드와 함께 `{ success: false, message: '...' }` 일관된 JSON 객체를 반환합니다.


  【카테고리 5: 미디어 스트리밍 & 네트워크 (Media Streaming & Network)】

  Q21. CCTV 라이브 모달에서 외부 웹캠/DroidCam 스트림을 어떻게 렌더링했나요?
  → 외부 스트리밍 URL을 `<iframe>` 컴포넌트로 래핑하여 HTML 기반 웹 플레이어 및 MJPEG 피드를 
    모달 내부 크기에 맞게 100% 동적으로 렌더링했습니다.

  Q22. CCTV 스마트폰 촬영 시 세로/가로 화면 비틀림은 어떻게 해결했나요?
  → `CctvLiveModal.tsx`에 `[🔄 회전]` 버튼을 구현하고 CSS `transform: rotate(90deg) scale(1.35)` 
    트랜지션을 적용하여 세로 촬영 피드도 가로 관제 화면에 맞게 비율 확장을 보정했습니다.

  Q23. 비디오 영역 더블클릭 시 유튜브 스타일 전체 화면 작동 원리는?
  → 비디오 컨테이너에 `onDoubleClick` 이벤트를 바인딩하고 `isFullscreen` 상태를 토글하여 
    CSS `fixed inset-0 w-full h-full z-50` 최상단 오버레이 레이아웃으로 전환되게 구현했습니다.

  Q24. CCTV 연동 설정 URL의 영속성은 어떻게 관리하나요?
  → 입력받은 스트리밍 URL을 브라우저 `localStorage`('cctv_streaming_url')에 저장하여 
    새로고침 후에도 이전에 연동했던 카메라 주소가 자동 유지되도록 처리했습니다.

  Q25. 서로 다른 네트워크(사무실 LAN PC ↔ 5G 스마트폰) 간 무선 스트리밍 해결책은?
  → Tailscale 가상 사설망(VPN) 또는 ngrok 터널링을 이용해 두 기기 간 P2P 보안 무선 통로를 
    개설하고, `100.X.X.X` 메쉬 IP를 통해 사설망 제약 없이 스트리밍을 수신합니다.


  【카테고리 6: 보안, 미들웨어 & 개인정보보호법 (Security & Compliance)】

  Q26. 미들웨어(middleware.ts)의 matcher 설정 목적은?
  → 정적 에셋(이미지, 폰트)을 제외하고, 보안 관리가 필요한 `/api/:path*` API 경로에만 
    선택적으로 미들웨어가 실행되도록 범위를 제한하여 성능 오버헤드를 방지했습니다.

  Q27. CORS Access-Control-Allow-Origin: * 설정이 필요한 이유는?
  → 모바일 시연 기기(/mobile-demo) 및 외부 IoT 게이트웨이가 다른 IP/포트에서 
    관제 API로 Cross-Origin 요청을 보낼 때 브라우저 차단을 방지하기 위함입니다.

  Q28. OPTIONS 프리플라이트 요청을 미들웨어에서 204로 즉시 응답하는 이유는?
  → 브라우저가 PUT/DELETE 등 실제 요청 전 보내는 사전 검증 요청에 즉시 204 No Content를 
    응답하여 API 통신 지연 시간을 줄이고 응답성을 높이기 위함입니다.

  Q29. 개인정보보호법 준수를 위한 인명 위치 마스킹 알고리즘은?
  → 평시(`isOtpApproved === false`)에는 `OccupantLayer`가 `null`을 반환하여 인원 위치와 
    아이콘을 DOM에서 완전히 은폐하고, API 역시 0명 데이터를 반환하도록 다중 차단했습니다.

  Q30. 119 OTP 상황 종료(REVOKE) 시 일어나는 동작은?
  → POST /api/emergency { action: 'REVOKE' }를 호출하여 인메모리 세션을 해제하고, 
    `useOccupantStore.resetOccupants()`를 실행하여 인명 데이터를 재마스킹 상태로 복귀시킵니다.


  【카테고리 7: 소방 관제 도메인 로직 & 실무 반영 (Domain Logic)】

  Q31. 소화기 내용연수 10년 법령을 시스템에 어떻게 반영했나요?
  → IoT 센서 노드의 배터리 수명 및 상태 점검 주기를 10년 주기 케어로 연동하여 
    `MAINTENANCE` 점검 상태로 자동 전환되는 관제 로직을 설계했습니다.

  Q32. 비상문 자동개폐기의 4단계 상태 구분 기준은?
  → 소방법 및 KFI 인증 규격에 따라 `LOCKED`(평시 잠금), `UNLOCKED`(해제), 
    `OPENED`(비상 개방), `CLOSED`(닫힘) 4단계 상태 배지와 자동 닫힘 타이머를 시각화했습니다.

  Q33. Web Audio API를 활용한 소방 경보음 합성의 장점은?
  → 외부 오디오 MP3 파일 로딩 지연이나 파일 손상 위험 없이, 800Hz 사인파 펄스를 
    브라우저에서 0ms 즉시 합성 재생하여 긴급 상황 전달력을 높였습니다.

  Q34. B2 지하주차장 EV 충전기 15대 관리 모달의 역할은?
  → 충전기 상태(충전중/대기/점검/폐기) 실시간 요약 카드 제공 및 신규 충전기 설치/삭제 
    CRUD를 제공하여 전기차 화재 위험 구역을 집중 관리합니다.

  Q35. 소방점검 이력 관리 모달(FireLogManageModal)의 검색/필터 메커니즘은?
  → 검색어(내용/검사자), 층 선택 드롭다운, 점검 결과(PASS/WARNING/FAIL) 3가지 조건이 
    동시에 적용되는 `Array.prototype.filter()` 다중 조합 필터링으로 빠르게 점검 로그를 탐색합니다.
